0. role

you are a senior software architect, staff-level next.js engineer, product engineer, and ui/ux engineer.

you are implementing echolens, an ai-powered media and information literacy platform.

this is a 20-hour prototype, not a full production-scale implementation.

the prototype must feel polished, coherent, intelligent, and functional.

the goal is to demonstrate the complete echolens product experience through a reliable vertical slice.

1. non-negotiable project rule

do not worsen, simplify, replace, or overcomplicate the architecture defined in this document.

before implementing anything:

understand the existing architecture.
preserve existing decisions.
reuse existing components and utilities.
do not introduce a new library when an existing dependency can solve the problem.
do not introduce infrastructure that is unnecessary for the prototype.
do not replace a working implementation with a more complicated implementation.
do not create placeholder architecture that will need to be thrown away.
do not build infrastructure merely because it would exist in a theoretical production system.
prioritize the complete user journey over backend sophistication.
every implementation decision must support the actual echolens experience.

if something is too expensive to implement within the prototype timeline, hardcode or deterministically simulate it rather than damaging the core architecture.

2. project objective

echolens is an ai-powered information literacy companion.

its purpose is not to tell users:

what to believe
which political/social perspective is correct
which side is morally superior
whether they are biased
whether their opinion is stupid

instead, echolens helps users understand:

what information they have encountered
what perspectives they have considered
what evidence they have encountered
what dimensions they have not considered
what context may be missing
how different claims connect to evidence and sources
how their understanding changes after exploration
core value proposition

we don't tell you what to think.
we show you what you may be missing.

3. central product philosophy

echolens must always follow these principles:

do not tell users what to believe.
do not decide which perspective is correct.
do not label users as biased, stupid, ignorant, or politically aligned.
do not manipulate users toward an ideology.
do not optimize recommendations purely for engagement.
make the information ecosystem visible.
expose missing context, evidence, and perspectives.
encourage critical thinking through interaction.
distinguish facts, claims, opinions, interpretations, and uncertainty.
explain why information is being recommended.
preserve user agency.

the product should help users form more informed opinions, not force them to change opinions.

4. important privacy rule

echolens must never claim to monitor a user's complete browsing history, private messages, private social feeds, or private communications.

the prototype should operate on:

selected topics
public/trending topics
user-entered topics
pasted URLs
pasted text
uploaded screenshots/documents where implemented
curated demo content

behavioral signals can be used only to understand the user's interaction with echolens.

do not infer sensitive psychological, political, religious, medical, or demographic attributes.

the "awareness profile" describes the user's interaction and information coverage for the selected topic, not their identity.

avoid calling the profile a personality diagnosis.

this is the most important flow in the entire application.

user enters echolens
        ↓
trending topic discovery
        ↓
topic selection
        ↓
interactive case study
        ↓
user answers scenario-based questions
        ↓
echolens understands current information coverage
        ↓
awareness profile
        ↓
explored perspectives
        ↓
unexplored perspectives
        ↓
user selects an unexplored dimension
        ↓
dynamic information branch opens
        ↓
deeper nodes
        ↓
claims / evidence / context / sources / related issues
        ↓
articles / reports / books / videos / primary sources
        ↓
user explores
        ↓
profile updates
        ↓
user may:
    ├── explore another dimension
    ├── view recommendations
    ├── view awareness profile
    └── return to case study
             ↓
      new questions
             ↓
      updated awareness profile
             ↓
          repeat loop

this loop is the core of echolens.

8. topic selection

when a user selects a topic, do not immediately show a long article.

show:

topic title
short context
why the topic matters
information dimensions
start case study button

primary CTA:

9. interactive case study

this is the first major interaction.

the case study must be adaptive.

it should not behave like a conventional quiz.

questions should explore:

assumptions
interpretation
evidence
priorities
possible causes
consequences
stakeholder viewpoints
uncertainty
source selection

questions are not simply:

correct / incorrect

instead they should reveal:

how does this user currently approach the issue?

10. branching case-study architecture

case studies may be hardcoded.

example:

question 1
   │
   ├── evidence-oriented answer → question 2
   │
   ├── stakeholder-oriented answer → question 3
   │
   └── assumption-oriented answer → question 4

different users should therefore experience different paths.

case studies should contain approximately:

4–13 steps
depending on the user's choices

do not make every path identical.

the system should record:

dimensions encountered
dimensions ignored
evidence preference
source preference
stakeholder consideration
context consideration
reasoning path

17. awareness profile update loop

the user must be able to return to the case study.

when they return:

do not simply replay the same questions.

show a new question set or alternate branch based on the dimensions they explored.

example:

first attempt
→ user ignored historical context

exploration
→ user studies historical context

second case study
→ historical-context question appears

after the second attempt:

profile updated

the dashboard should visibly communicate change over time.

19. technical architecture

use the following architecture for the prototype.

frontend
next.js
react
typescript
tailwind css
shadcn/ui
lucide-react
framer motion
react flow
recharts
backend

use next.js server functionality.

prefer:

server components by default
server actions where appropriate
route handlers only when necessary

do not introduce a separate backend unless absolutely necessary.

ai

use a single configurable llm provider.

the implementation must isolate AI calls behind:

lib/ai/

or equivalent.

the application must not scatter provider-specific calls throughout the UI.

AI should be used for:

content understanding
summaries
contextual explanations
recommendation explanations
optional dynamic content interpretation

hardcoded deterministic logic should control:

case-study branching
scoring
topic dimensions
prototype recommendations
graph relationships

  topics.ts
  case-studies.ts
  perspectives.ts

32. implementation rule

before adding any feature, ask:

if no:

do not implement it.
